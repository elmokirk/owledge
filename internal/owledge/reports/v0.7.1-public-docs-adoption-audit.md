# v0.7.1 Public Documentation and Adoption Audit

## Audit boundary

This audit compares the public documentation on remote `main` at `fd83571`
with the current roadmap branch at `8f5c8a0`. The public README and docs are
unchanged on the roadmap branch, so the findings apply to both surfaces.

Reviewed entrypoints: `README.md`, `docs/README.md`, `docs/quickstart.md`,
`docs/integration-decision-guide.md`, `docs/agent-integration-guide.md`,
`docs/agent-first-run-setup.md`, `docs/install-plugin.md`,
`docs/harness-plugin-matrix.md`, `docs/agents-md-integration-block.md`,
`standalone-skills/README.md`, and the v0.7.1 adoption tickets and gate.

Mechanical baseline:

- `python tools/owledge.py test public-docs --project-root .`: passed, 233 checks.
- `python tools/validate_v1_delivery_plan.py`: passed, 56 tickets and 25 gates
  before this audit was integrated.

The mechanical checks do not test whether a beginner understands the product,
whether integration axes are separated, or whether an agent can execute a
complete installation recipe without interpretation.

## Findings

### P0 - The first-screen story lacks a complete mental model

The README states the problem and lists artifacts, but the first complete
workflow appears after installation, decision, harness, and integration
sections. A new reader sees commands before understanding the lifecycle from
project truth to scoped context, agent work, evidence, handoff, and reviewed
promotion.

Required correction: lead with audience, trigger problems, outcomes, and
non-goals; show one small end-to-end Mermaid lifecycle before any install
command; explain what is read, written, private, and generated; move repository
layout, add-on inventory, benchmarks, and maintainer gates below the adoption
path or into linked docs.

### P0 - Four independent choices are presented as one integration ladder

Current docs mix:

1. product footprint: principles-only, project kit, knowledgebase module;
2. package delivery: `uvx`, persistent `uv tool`, or source checkout;
3. runtime connection: instruction file, skill, plugin/hooks, or read-only MCP;
4. optional capability: add-ons and standalone workflow skills.

These are not mutually exclusive. A project-local kit can also use a runtime
adapter and one standalone skill, while `uvx` is a delivery mechanism rather
than an integration mode. Define these as orthogonal axes and provide a
decision table that produces one complete recipe.

### P0 - Installation command chains are not self-contained

Examples switch between `uvx owledge`, persistent `owledge`, and
`python tools/owledge.py` without always stating which checkout or install
makes the next command available. The README's fast proof begins with `uvx`
and then invokes persistent `owledge`; the quickstart similarly recommends
`uvx` and verifies with `owledge`. Source-checkout commands do not consistently
say that they must run from the Owledge checkout.

Required correction: create a dedicated Installation Hub linked near the top;
give one copy-paste chain per supported delivery method; specify prerequisites,
working directory, expected writes/output, verification, rerun behavior,
upgrade, uninstall, and recovery; smoke-test commands extracted from docs.

### P0 - Agent integration guidance is descriptive, not executable

The plugin guide uses phrases such as "plugin flow when available" and
"configured plugin area" without an authoritative destination or bounded
support statement for every runtime. Several verification commands test the
Owledge maintainer checkout or release readiness instead of the host project's
chosen integration. The agent first-run guide requires a source checkout even
though the public path is package-first.

Required correction: split human and agent entrypoints while retaining one
canonical command contract; give agents preflight, exact allowed writes,
idempotency, success output, recovery, and stop/escalate rules; publish
runtime-specific recipes only where locally verified.

### P1 - Skills, principles, plugins, and add-ons need a stable taxonomy

"Principles-only / Skills" combines a policy layer with task-triggered
workflow skills. The full-kit skills, standalone skills, runtime plugin, MCP
surface, and add-ons lack one contract explaining when each is loaded and
whether it writes project memory.

Required correction: separate policy skill, workflow skills, runtime adapters,
and add-ons; document trigger, input, output, side effects, dependencies,
runtime support, and stability; define precedence among `AGENTS.md`,
`OWLEDGE.md`, skills, and hooks; diagram skill invocation and promotion.

### P1 - Benefits are artifact-led rather than outcome-led

The README describes plans, evidence, handoffs, and indexes, but does not
quickly translate them into less re-explaining, safer agent changes, resumable
work, inspectable state, and easier runtime switching. Pair every capability
with a user problem, observable outcome, and boundary.

### P1 - Non-goals are correct but too late

Place them beside the product explanation so readers do not infer that
Owledge is an agent runtime, hosted memory service, vector database, automatic
truth engine, or replacement for project management and coding methods.

### P1 - The docs index is a link inventory, not a learning path

`docs/README.md` does not cleanly separate concepts, installation,
integrations, workflows, reference, and maintainer material. Establish
task-oriented navigation with one canonical page per concern.

## Proposed public information architecture

```text
README.md                         product story and route selection
docs/README.md                    documentation home and learning paths
docs/why-owledge.md               why, when, benefits, and non-goals
docs/how-owledge-works.md         lifecycle and read/write/privacy boundaries
docs/install/README.md            installation hub and route matrix
docs/install/project.md           project package/source recipes
docs/install/knowledgebase.md     additive vault/module recipe
docs/install/principles-only.md   instruction-only recipe and limits
docs/install/agent-guided.md      bounded copy-paste agent contract
docs/integrations/README.md       runtime integration model
docs/integrations/<runtime>.md    only verified runtime-specific recipes
docs/workflows/README.md          plan, context, execute, evidence, resume
docs/skills/README.md             policy/workflow skill taxonomy
docs/reference/                   CLI, schemas, compatibility, maintenance
```

Exact filenames remain an owner decision. The required contract is one
canonical page per concern, shallow README navigation, and no duplicated
command truth.

## Required diagrams

1. Product lifecycle: intent -> project truth -> scoped context -> agent work
   -> evidence/handoff -> reviewed promotion.
2. Integration axes: footprint plus delivery plus optional runtime adapter plus
   optional capabilities.
3. Read/write/privacy boundary: canonical Markdown, private runtime capture,
   generated views, and reviewed exports.
4. Skill invocation: intent -> policy/workflow skill -> candidate artifact ->
   QA/review -> optional canonical promotion.
5. Resume: checkpoint/handoff -> next agent/runtime -> scoped context -> gate.

## Owner decisions required before implementation

1. Is the primary beginner default the project-local kit, or should
   principles-only remain recommended despite its smaller durable surface?
2. Should the category phrase be "project knowledge and agent delivery layer",
   "durable project memory", or another statement?
3. Which runtime installs have exact reproducible destinations today: Codex,
   Claude Code, Cowork, and/or generic MCP?
4. Is `uv` a required beginner prerequisite, or must a Python/pip alternative
   receive equal support?
5. Should v0.7.1 introduce directory URLs (`docs/install/`,
   `docs/integrations/`) or preserve flat URLs and improve navigation first?
6. Which existing skills are public product surface versus maintainer or
   experimental workflows?

## Audit verdict

The docs are mechanically healthy but adoption-incomplete. `OW-071-04` and
`OW-071-05` name the right outcome but compress product narrative,
installation truth, workflows, and skills/agent integration into work that
cannot be independently reviewed. Expand v0.7.1 Phase 071-B before public
adoption claims or release work continue.
