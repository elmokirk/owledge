# v0.7.1 Docs Adoption External User and CTO Review

## Subject and question

Can an external agentic-tools power user or senior agentic engineer understand
why Owledge exists, how it works, what it installs, what is automatic, how to
use it effectively, and which global/hub capabilities are real today?

## Reviewers

- UX/DX Power-User: adoption, integration choices, first proof, footprint,
  skills, and daily workflow.
- CTO / Senior Agentic Engineer: implementation truth, harness boundaries,
  Owlib/global/hub architecture, server safety, and roadmap coherence.

Both reviewers were independent read-only subagents using `agentic-review` and
the repository's `REVIEW.md` policy.

## Evidence

- Public README and core docs.
- `pyproject.toml`, package contents, clean quickstart output, CLI help.
- `AGENTS.template.md`, skills, runtime plugin, MCP and HTTP core code.
- Owlib, Global User Knowledge Layer, Cross-Project Hub Kit.
- v0.7.1 plan, tickets, gates, and v1 roadmap.

## Consolidated findings

### P0 - Public package demo is not executable as written

The README starts with `uvx owledge quickstart` and then uses persistent
`owledge install-addon`; the wheel deliberately excludes add-ons/plugins. The
five-minute guide instead requires a source checkout. Package-only, persistent
tool, and source demo paths need separate executable contracts.

### P0 - Owlib still reads the legacy project layout

Owlib currently expects `PROJECT_CONTEXT.md` and `agent-memory/`, while v0.7
projects use `OWLEDGE.md` and `.owledge/`. Current Hub claims must remain
preview/legacy until `OW-071-06` proves both current and migration fixtures.

### P0 - The shipped HTTP server is an unclassified development prototype

`tools/owledge_core.py serve` exposes token-authenticated task, evidence, gate,
context, promotion, and export writes. It has useful SQLite, lease, token, and
tenant primitives, but lacks a production remote security/deployment contract.
Remote bind, public health details, actor-to-tenant authorization, TLS,
rotation/revocation, limits, backup/restore, observability, and conflict rules
are not release-ready.

### P1 - Pre-install footprint and ownership are not public contracts

"Minimal" currently refers to optionality, not file count. A clean project kit
creates 152 files. Every preset must disclose download size, created/skipped
files, folder purpose, canonical/private/generated ownership, rebuildability,
upgrade, and uninstall impact before installation.

### P1 - Automatic versus manual behavior is not explicit

`AGENTS.md` is harness-consumed policy, not a scheduler. Skills are
intent/user-triggered. Hooks only capture events when installed. CLI commands
perform deterministic work when invoked. Curator promotion remains explicit.
Document action, actor, trigger, side effect, and default for every lifecycle
step.

### P1 - Users need presets and a concrete operating sequence

The four axes are correct but insufficient alone. Publish named presets and a
canonical loop:

`preflight -> intent -> scoped context -> plan -> execute -> evidence ->
independent review -> handoff/checkpoint -> optional promotion -> rebuild views`

Each step must say whether it is an instruction, skill, hook, CLI, or human
decision. Provide variants for small work, existing repo, standalone project,
KB, multi-agent, and global reuse.

### P1 - Four different global/hub concepts need separate names

- Global user memory: private personal cross-project context.
- Cross-Project Hub Kit: local static map of reviewed shared records.
- Owlib: local central index/candidate engine; current-layout compatibility is
  still planned in v0.7.1.
- Team Hub/Server: remote synchronization/service; not supported today and
  explicitly post-v1 for hosted/multi-tenant form.

### P1 - Capability maturity must be visible

Every public capability needs `available`, `local experimental`, `preview`,
`planned`, or `post-v1`, with code/gate evidence for current claims.

### P2 - README needs a strict information budget

Before the first install block: one-sentence abstract, three problem/outcome
pairs, one lifecycle diagram, non-goals, and Try/Install/Understand/Integrate
routes. Move repo layout, add-ons, benchmark detail, and maintainer material.

### P2 - Test paths need three distinct proof levels

- 30 seconds/no install: understand the contract and inspect an example.
- 5 minutes/package-only scratch target: create, verify, explain, and reset.
- Cross-session agent proof: a fresh agent resumes from documented entrypoints
  without chat history.

## Required owner decisions

1. Default entry: no-install principles trial or project-local kit?
2. Is principles-only truly fileless, with a separate manual mini-kit?
3. Exact meaning of automatic across instruction, discovery, hooks, CLI, and
   background process?
4. Supported versus advanced/experimental/maintainer skills?
5. Official skill and workflow sequence?
6. Global installation: shared tools only, private user context, project
   registry, or a defined combination?
7. Owlib relationship: core Owledge component or separately versioned companion?
8. HTTP control plane: product, internal harness, or historical prototype?
9. Future team sync: Git/CI, push agent, pull daemon, or server API?
10. Conflict authority: project Markdown, Hub projection, issue tracker, or
    explicit curator policy?
11. Team Hub tenancy: single-tenant deployment or multi-tenant service?
12. Supported runtime adapters with reproducible clean-machine evidence?
