# v0.7.1 Public Documentation Adoption Plan

## Goal

Make a new user or coding agent able to answer, before installing:

- why and when Owledge is useful;
- which problems and outcomes it addresses;
- what it does not do;
- how information moves through the system;
- which footprint, delivery method, runtime adapter, and skills apply;
- how to install, verify, recover, upgrade, and remove the selected path.
- how large each preset is, which files/folders it adds, and who owns them;
- what is automatic, agent-triggered, user-triggered, or curator-controlled;
- which global, cross-project, Hub, and server capabilities exist today.

## Non-goals

- No new hosted service, runtime marketplace claim, or write-enabled MCP.
- No capability claim without current release evidence.
- No duplicate CLI truth across pages.
- No docs workaround for an install path that fails a clean smoke test.
- No maintainer-doc redesign until beginner navigation is stable.

## Release placement

This expands v0.7.1 Phase 071-B and remains blocked by `OW-071-02`. It must
complete before `OW-071-05` proves the golden demo and before `OW-071-08` cuts
the release candidate.

## Owner decisions recorded 2026-07-22

- Public product category: **Agentic Engineering Context & Planning Layer**.
  Search-oriented alternatives are **Context Engineering & Agent Memory for
  Coding Agents** and **Agentic SDLC Knowledge & Observability Layer**.
- Principles-only ships first as one compact, runtime-independent
  `owledge-contract`. Additional skills qualify only when they work without the
  Owledge runtime and require no rewrite; otherwise they remain out of scope.
- Owlib is the future central synchronization and intelligence interface across
  projects: reviewed agent learnings, parallel project extraction, PI
  intelligence, and agent-maintenance knowledge. Before v1 it remains local,
  explicit, and subordinate to project truth.
- The future Team Hub is a post-v1 multi-tenant service vision. It has no v1
  delivery priority; v1 first proves exceptional local value for one user.
- Required v1 harness profiles are Codex, Claude Code, OpenCode, and Hermes.
  Hermes starts as the required read-only profile; a Pi.dev
  planning/documentation adapter is post-v1 exploration.
- Git/CI synchronization and the remote Sync Layer are post-v1 work, not v1
  dependencies or public current-capability claims.

## Phase 0 - Technical truth and local server boundary

Ticket: `OW-071-13`.

Classify the shipped HTTP control plane as product, internal harness, or
development prototype; close unsafe public ambiguity; make non-loopback
behavior, health disclosure, actor/tenant authorization, payload limits, and
negative security behavior explicit and tested. Produce a capability maturity
source that docs can label `available`, `local experimental`, `preview`,
`planned`, or `post-v1`.

QA gate: remote exposure is either blocked by default or covered by an approved
security/deployment contract; public docs cannot imply a supported team server.

## Phase 1 - Product narrative and information architecture

Ticket: `OW-071-04`.

Deliver a first-screen value proposition, why/when, benefits, boundaries,
non-goals, an early lifecycle diagram, a routing-focused README, a staged docs
home, an `implemented/experimental/planned/post-v1` truth matrix, a strict
pre-install information budget, and owner-approved category/default decisions.

QA gate: a five-second fixture identifies audience, problem, outcome, boundary,
and next action; no install command appears before the mental model; claims map
to current evidence or explicit roadmap labels.

## Phase 2 - Installation hub and executable command truth

Ticket: `OW-071-10`.

Deliver a top-linked Installation Hub; separate footprint, delivery method,
runtime adapter, and optional capability; publish only supported complete
recipes; specify prerequisites, working directory, writes, output, verify,
idempotency, recovery, upgrade, and uninstall; establish one command source.
For every preset, generate download size, created/skipped file count, folder
purpose, canonical/private/generated ownership, rebuildability, and removal
impact from a clean release artifact.

QA gate: extracted chains pass on clean Windows, macOS, and Linux fixtures; a
package-only recipe never assumes a checkout or persistent binary; source
recipes name both roots; unsupported wiring is labelled.

## Phase 3 - How Owledge works and workflow visualization

Ticket: `OW-071-11`.

Deliver the canonical lifecycle; read/write/privacy and
canonical/candidate/generated boundaries; workflow pages for setup, context,
planning, execution, evidence, review, handoff, resume, KB, and MCP; Mermaid
diagrams with prose fallbacks; a beginner glossary; an action-by-actor matrix
covering instruction compliance, harness discovery, hooks, skills, CLI, MCP,
curation, sync, and background processes; an effective daily best-practice loop
with small-task, existing-repo, standalone, KB, and multi-agent variants.

QA gate: a beginner can narrate the lifecycle and locate every shown artifact;
diagrams agree with templates, CLI behavior, and privacy rules; Owledge is not
represented as a runtime, truth engine, or hosted store.

## Phase 4 - Skills taxonomy and agent integration contracts

Ticket: `OW-071-12`.

Deliver distinct categories for policy/principles, workflow skills, runtime
adapters, MCP, and add-ons; a public registry with trigger, IO, side effects,
dependencies, runtime support, and stability; precedence/read order; shared
human and agent command truth; agent preflight, allowed writes, success report,
recovery, and stop rules; a skill invocation/promotion diagram; an official
happy-path skill sequence plus explicit situational/advanced alternatives.
The runtime-independent `owledge-contract` is the Principles-only default;
runtime-coupled skills are excluded from that preset rather than rewritten.

QA gate: fixture agents select the correct path; no recipe relies on implied
plugin folders or unverified features; verification proves the host project.

## Phase 5 - Adoption presets and Global/Hub status

Ticket: `OW-071-14`.

Publish named presets for no-install principles, manual mini-kit, existing
project, new standalone project, existing Markdown KB, runtime adapter, private
global user layer, and cross-project power-user use. Separate `global-memory`,
Cross-Project Hub Kit, Owlib, the local HTTP prototype, and a future Team Hub.
Each row states current maturity, value, data authority, automation, privacy,
requirements, limitations, and upgrade path.

Document the Team Hub only as the post-v1 multi-tenant direction: a central
planning and reviewed-learning layer for agents, projects, and teams. Do not put
remote Git/CI sync, hosted tenancy, or cross-team automation on the v1 path.

QA gate: a user can choose a preset without interpreting implementation files;
no local Hub capability is represented as automatic remote team sync; current
Owlib claims are gated by `OW-071-06` or labelled preview/legacy.

## Phase 6 - Golden journey and adoption proof

Ticket: `OW-071-05`.

Deliver three distinct proofs: a 30-second no-install mental-model/example path;
a package-only five-minute scratch journey with expected output, verification,
and reset; and a fresh-session/second-agent resume journey using only documented
entrypoints. Source-only add-on demos remain separate and labelled.

QA gate: `G-071-B-ADOPTION`.

## Execution lanes

- Narrative: `OW-071-04`; README and navigation.
- Install: `OW-071-10`; command truth and install fixtures.
- Workflow: `OW-071-11`; lifecycle and diagrams.
- Skills/agent: `OW-071-12`; taxonomy and runtime recipes.
- Adoption/Hub: `OW-071-14`; presets and maturity boundaries.
- Proof: `OW-071-05`; starts after all five doc deliverables integrate.

Overlapping `README.md` and `docs/README.md` edits belong to the integration
owner; lane workers propose routed sections rather than merging competing edits.

## Definition of Done

- All six audit owner decisions are resolved or explicitly deferred with
  bounded public wording.
- `OW-071-13`, `OW-071-04`, `OW-071-10`, `OW-071-11`, `OW-071-12`,
  `OW-071-14`, and `OW-071-05` have independent QA evidence.
- README explains value and operation before installation detail.
- A dedicated Installation Hub provides supported end-to-end recipes.
- Skills and runtime integration surfaces are not conflated.
- Pre-install footprint, automation, maturity, and Global/Hub boundaries are
  generated from or traced to current implementation evidence.
- Human and fixture-agent journeys reach value without maintainer interpretation.
- Public-docs, command, link, fixture, privacy, and adoption gates pass from a
  clean integration commit.
