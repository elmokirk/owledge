# v0.7.1 Release Execution Orchestration Plan

## Outcome and Promotion Boundary

Produce a clean, committed, reproducible Owledge v0.7.1 release-candidate
tree. This plan does not publish, tag, push, merge, or start v0.8.0. Release
publication remains an owner action after `G-071-RC` and
`G-071-ALIGNMENT`.

The canonical ticket scope remains
`internal/owledge/workpackages/owledge-v1-autonomous-delivery/tickets/ALL-TICKETS.md`.
This plan controls execution order, path claims, commits, independent review,
and recovery only.

## Hard Constraints

- WIP is one ticket per implementation agent.
- No subagent edits `README.md`, `docs/README.md`, release notes, central
  checklists, `BACKLOG.yaml`, or `RUN-STATE.yaml`; the orchestrator owns them.
- Agents use disjoint allowed paths and return evidence-linked handoffs.
- QA and Red Team reviewers are read-only and independent of implementation.
- No ticket becomes `done` without positive and negative evidence.
- No generated artifact is accepted after source drift.
- No release build, tag, or publication from a dirty tracked tree.
- Every phase ends with a reflection: findings, decisions, next-plan effect,
  and exact resume action.

## Phase 0 - Foundation Freeze and Phase Commit

Scope: the completed Handoff Decision Bridge, version-reflection control
plane, bounded planning modes, reliable skill discovery, tests, and refreshed
evidence currently present in the working tree.

Actions:

1. Run independent diff-scope, release-contract, and blindspot reviews.
2. Fix only validated blocking findings.
3. Run targeted tests and delivery-plan validation on the working state.
4. Create cohesive source commits while excluding regenerated evidence.
5. Capture the clean source SHA and run all finalization gates from that state.
6. Commit only reproducible, sanitized evidence that records the tested source
   SHA/tree identity.
7. Verify no source drift and record the final clean-tree state.

Gate: zero P0/P1 review findings, validator green, non-vacuous 38/38
finalization gates, `git diff --check` green, evidence bound to tested source,
and clean tracked tree after the evidence commit.

## Phase 1 - Truth Register (`OW-071-01`)

Run serially because every later v0.7.1 ticket depends directly or indirectly
on its normalized work state.

Implementation lane:

- reconcile live roadmap/checklist/status claims without deleting history;
- give every open item state, source, gap, target release, owner, and evidence;
- add a deterministic roadmap/state validator and stale-state negative fixture;
- write ticket evidence and QA handoff.

Independent QA lane: roadmap auditor verifies contradictions, historical
checkbox behavior, and version truth against the worker commit. The worker
creates one cohesive ticket commit and evidence manifest in an isolated
worktree; the orchestrator alone updates canonical central state and integrates
the reviewed commit.

Gate: `OW-071-01` accepted; `OW-071-02`, `OW-071-03`, and `OW-071-13` become
dependency-ready.

## Phase 2 - Truth and Baseline Parallel Wave

Run only after Phase 1:

| Ticket | Implementation lane | Primary path claim |
| --- | --- | --- |
| `OW-071-02` | release/version contract | version, changelog, upgrade/release contract tests |
| `OW-071-03` | benchmark truth | benchmark tooling, fixtures, evaluation evidence |
| `OW-071-13` | local HTTP safety boundary | HTTP control plane, security fixtures, capability maturity evidence |

Each lane receives one follow-up review at most. The orchestrator resolves
overlap, updates central artifacts, and creates separate ticket commits where
the diff remains reviewable.

Gate: independent `G-071-A-TRUTH` review proves all four tickets and cumulative
negative checks.

## Phase 3 - Product Narrative Foundation (`OW-071-04`)

Implement the beginner-first product story and information architecture before
parallel documentation work. The orchestrator owns central README/navigation;
one scoped agent may draft non-central pages or fixtures.

Gate: five-second comprehension fixture, claim/evidence mapping, public-docs
gate, and beginner review.

## Phase 4 - Parallel Adoption Documentation

After `OW-071-04`, run non-overlapping lanes:

| Ticket | Lane |
| --- | --- |
| `OW-071-10` | installation hub and executable command truth |
| `OW-071-11` | lifecycle, workflow, diagrams, privacy boundaries |
| `OW-071-12` | skill taxonomy, discovery, agent/runtime contracts |
| `OW-071-14` | adoption presets and Global/Hub maturity |

Subagents edit only assigned new or dedicated pages/fixtures. Central README
and index integration stays with the orchestrator.

Gate: extracted commands, link/Mermaid checks, fixture-agent selection,
cross-platform install review, architecture/privacy review, and power-user
review.

## Phase 5 - Golden Adoption Proof (`OW-071-05`)

Integrate the completed documentation into the 30-second principles path,
package-only five-minute path, and fresh-session resume proof.

Gate: `G-071-B-ADOPTION` from the committed integration state.

## Phase 6 - Compatibility Wave

Run `OW-071-06` and `OW-071-07` in parallel only with explicit path claims:

- Owlib current-layout compatibility and privacy;
- Hermes required read-only profile and degradation truth.

Gate: `G-071-C-COMPAT`.

## Phase 7 - Release Candidate and Owner Alignment

`OW-071-08`:

1. freeze source;
2. run cumulative gates from the clean commit;
3. build wheel and sdist;
4. install both in clean temporary environments;
5. run package/source/plugin smoke tests;
6. generate release evidence and candidate notes;
7. commit release artifacts only after source checks remain reproducible.

`OW-071-09`:

- compile the eleven-section v0.7.1 update;
- expose every finding, decision, limitation, and v0.8.0 plan effect;
- stop for owner `approve`, `adjust`, or `defer`.

No tag, push, publication, merge, or v0.8.0 execution is implied.

## Commit Strategy

1. `chore(v071): harden version reflection and delivery control plane`
2. `feat(skills): add bounded delivery modes and reliable discovery`
3. `docs(v071): document planning modes and release orchestration`
4. `test(v071): refresh frozen foundation evidence`
5. `feat(v071/OW-071-01): normalize live work state`
6. ticket-scoped Phase 071-A/adoption/compatibility commits
7. `test(v071): complete release candidate evidence`
8. `docs(v071): prepare release update and alignment handoff`

After Phase 0, the orchestrator creates `codex/v071-integration`. Each ticket
uses an isolated `codex/v071-<ticket>` worktree/branch and creates one cohesive
commit plus manifest. Local serial execution is the usage-efficient default.
Specialist subagents are reserved for genuinely independent high-risk gates or
non-overlapping work where the expected review value exceeds context cost;
they are not spawned per run or per ticket by default. Only the orchestrator
integrates accepted work, updates central state, reruns cumulative checks, and
may create an evidence-only commit. No worker may merge, tag, publish, push,
or alter orchestrator-only files.

## Definition of Done

- All v0.7.1 tickets are independently accepted.
- `G-071-A-TRUTH`, `G-071-B-ADOPTION`, `G-071-C-COMPAT`, and `G-071-RC` pass
  from source-linked commits.
- Wheel/sdist install and runtime smoke evidence is reproducible.
- Tracked working tree is clean.
- v0.7.1 release update contains complete findings and decisions.
- Owner alignment is awaiting `approve`, `adjust`, or `defer`.

## Resume State

Phase 1 and `OW-071-01` are complete at accepted commit `86871c6`. Resume Phase
2 at `OW-071-02` using the bounded release-trust scope recorded in
`RUN-STATE.yaml`. Keep `OW-071-03` and `OW-071-13` serially blocked until the
preceding ticket is integrated, reflected, and the tracked tree is clean.
